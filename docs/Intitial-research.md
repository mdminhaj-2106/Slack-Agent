# Recorder: A Closed-Loop Autodocumentation Agent for Slack — Research & Build Brief

## TL;DR
- **Build a transparent, peer-toned Slack AI agent that captures decisions, commitments, blockers, and rationale at the moment they're spoken — combining a passive five-layer NLP detector with a low-friction in-flow confirmation prompt — and stores ONLY evidence pointers (permalinks + message `ts` + channel id) in a Slack Canvas, retrievable via `/why [topic]`.** The novel, judge-impressive combination is: Agents & AI Apps split-view + in-thread message shortcut/ephemeral confirm + an evidence-only Canvas "memory" + a closed-loop follow-up verifier.
- **On persona: choose a "senior-dev peer" tone with light, sparing wit — NOT a quirky mascot and NOT pure neutral utility.** HCI evidence shows a conscientious, competent, peer-framed agent maximizes workplace trust and information yield; humor helps engagement only when sparing and brand-aligned, and reciprocal/gradual self-disclosure by the bot reliably increases user disclosure.
- **The key technical constraint to design around: `conversations.history`/`replies` are throttled to 1 request/min for non-Marketplace apps — build as an internal app and process messages live via Events API.** Slack's Real-time Search API (`assistant.search.context`) is now **generally available (GA as of early 2026)** — no longer partner-gated — and is the primary retrieval path for `/why`. It requires the Agents & AI Apps feature enabled, granular `search:read.*` scopes, and an `action_token` received from event payloads rather than a freely callable bot token.

## Key Findings

### 1. What the product fundamentally is
Recorder is a **transparent, closed-loop autodocumentation agent**: it listens to natural Slack conversation, detects high-value knowledge artifacts (decisions, commitments, blockers, repeat questions, contradictions, knowledge-ownership concentration), prompts the author in-flow to confirm capture without leaving the thread, stores only verifiable pointers back to the original messages in a Canvas, and later verifies whether stated commitments and decisions were actually followed through. It is the merger of "DecisionLog" (active in-flow decision capture + `/why` retrieval) and "SIGNAL" (passive five-layer detection + a no-synthetic-content Canvas), unified by a closed-loop verification layer that existing tools lack.

### 2. The core problem is real and existing tools fail predictably
ADRs, Confluence, and Notion fail because capture is a separate "destination" task divorced from where work happens. The ADR community itself documents this: practitioners observe that "Wikis (Confluence, Notion, etc.) are where ADRs go to be forgotten — they're disconnected from the code, hard to discover, and rarely maintained." Even ADR advocates note developers resist the word "architecture" and the ceremony of "records," and that immutability ideals break down in practice (Martin Fowler/Nygard lineage; joelparkerhenderson ADR repo). This validates the Recorder posture: capture must happen *in flow*, and retrieval must be where work happens (Slack), not in a separate wiki.

The commitment-tracking space confirms the "open loop" gap. Tools like Claryti claim to detect commitment language ("I will send," "Can you review"), infer owners/deadlines, and track bi-directionally. Claryti's own marketing asserts: "Teams using automated tracking complete 91% of action items versus 61% with manual methods (Claryti, 2025)" and that "39% of commitments are never completed" — **self-reported vendor data, not peer-reviewed.** Critically, these are meeting/email tools, not Slack-native, and most don't verify follow-through against later events.

### 3. Passive elicitation — the five SIGNAL detection layers are buildable
Each layer maps to a realistic, hackathon-feasible technique:

- **Decision detector**: Academic work (Kim & Rudin, "Learning About Meetings," arXiv:1306.1927; Bui et al., "Summarizing Decisions in Spoken Meetings," using the AMI corpus) shows decisions in multi-party dialogue can be detected from "dialogue acts" and adjacency-pair structure (question→answer, suggestion→positive-feedback). For a hackathon, an LLM classification prompt (Claude/GPT function calling) over decision-signal phrases ("let's go with," "we decided," "final call") is far simpler than the CRF/dialogue-act classifiers in the literature and will hit high recall.
- **Commitment/promise detector**: A well-established task. Microsoft holds patents on "automatic extraction of commitments and requests from communications" (US10361981, US9170993), using NLP+ML to classify a sentence as containing a commitment and to track its *lifecycle state* (created → delegated → discharged → cancelled). Academic work confirms feasibility — Azarbonyad, Sim & White, "Domain adaptation for commitment detection in email," WSDM 2019; Prabhakaran et al., "Author Commitment and Social Power" (arXiv:1805.06016). Hackathon approach: LLM classification with high-recall prompts plus a confidence threshold to suppress false positives.
- **Repeat-question map**: The well-studied duplicate-question detection problem (Stack Overflow/Quora). Embedding-based cosine similarity is the standard lightweight approach; Bogdanova et al.'s CNN/Siamese method reaches ~92.9% on AskUbuntu/Meta Stack Exchange and fine-tuned BERT ~86.26% on Quora — but a hackathon should use off-the-shelf sentence embeddings + cosine similarity with a threshold (cheap and effective).
- **Bus-factor graph**: The literature models projects as bipartite people↔task graphs and computes bus-factor via network robustness (Piccolo et al., Design Science 2018; Jabrayilzade et al., "Bus Factor in Practice," ICSE-SEIP 2022). Exact bus-factor is NP-hard. For Slack, substitute "tasks" with channels/threads/topics and infer knowledge concentration from *who answers questions and participates in threads on a topic*; a hackathon can use a simple degree/participation-concentration heuristic.
- **Contradiction detector**: This is Natural Language Inference (NLI) — classify a statement pair as entailment/neutral/contradiction. Off-the-shelf models (`roberta-large-mnli`, trained on SNLI/MultiNLI) or an LLM prompt over candidate statement pairs (retrieved by semantic similarity, then NLI-checked) is the standard pipeline (cf. arXiv:2508.17127) and is hackathon-feasible.

### 4. Active elicitation methodology and persona — the decision-critical UX research
**Recommended persona: "senior-dev peer" — competent, conscientious, warm-but-concise, with sparing wit. Reject the quirky-mascot and the pure-neutral-utility extremes.** The evidence:

- **Conscientiousness wins for engagement.** Völkel & Kaya, "Measuring the Effect of Mental Health Chatbot Personality on User Engagement" (MUM '22, ACM), found that "our quantitative results indicate that a highly conscientious chatbot is likely to foster the highest user engagement." (Mental-health context — direction is robust but transfer of exact magnitude to a workplace scribe is uncertain.) This maps directly to a reliable, detail-oriented "scribe/peer" persona.
- **Moderate, balanced personality beats maximal personality.** 2026 research (reported via TechXplore, Desai/Rahman et al.) found users "prefer chatbots with moderate, balanced personality expression over those with highly extroverted or minimal traits, rating them higher in intelligence, enjoyment, trust, and likability," and that user–bot personality alignment increases satisfaction. This argues against a loud quirky mascot.
- **Expertise framing builds epistemic trust but costs warmth.** HCI work on "expertise-supportive" chatbots (arXiv:2601.16720) found users called them "trustworthy," "competent," "logical," and valued that answers were "straight to the facts" rather than "emotionally pandering" — but noted reduced social closeness. Conversely, a friend-like/peer framing buffers trust during failures: research on chatbot social role found "the friend-like chatbot proved more effective in mitigating trust erosion." The synthesis: frame Recorder as a knowledgeable *peer* (trust + relatability) who is concise and factual (epistemic credibility), not a cold utility and not a comedian.
- **Reciprocal, gradual self-disclosure reliably increases user disclosure.** In Liang et al., "Discovering Chatbot's Self-Disclosure's Impact on User Trust, Affinity, and Recommendation Effectiveness" (arXiv:2106.01666), "372 MTurk participants were randomized… We found that people's self-disclosure level was strongly reciprocal to a chatbot's self-disclosure level," with adaptive emotional disclosure maximizing yield. A companion 47-participant, 3-week study from the same program found "chatbot self-disclosure had a reciprocal effect on promoting deeper participant self-disclosure that lasted over the study period." Design implication: Recorder should open by briefly disclosing its own "reasoning" ("I flagged this as a decision because you said 'let's go with X' — want me to log it?") rather than cold-interrogating.
- **Formality should scale with sensitivity.** Research on conversational style (ACM, "Does Chatbot Language Formality Affect Users' Self-Disclosure?") found a formal style elicited more high-quality utterances when requesting sensitive information; casual is better for low-stakes. Implication: Recorder defaults to casual-peer for routine decision capture, shifts more formal when capturing higher-stakes commitments.
- **Humor: use sparingly.** Practitioner and academic consensus (and a behavior-change humor RCT, arXiv:2403.00365) is that humor boosts engagement only when sparing and brand-aligned; sarcasm is risky in text. The safe call for a workplace tool is light wit, never a sustained bit.

**Gamification: yes, but lightweight and intrinsic-motivation-aligned.** Meta-analytic and field evidence shows points/badges/leaderboards can raise engagement and knowledge-sharing, mediated by social interaction (ScienceDirect S2444569X24000696), but gamified work can *backfire* on engagement/well-being for frontline workers, moderated by willingness to participate (Hammedi et al., ScienceDirect S0148296319300992). Self-determination-theory work shows gamified systems work through intrinsic motivation (competence, autonomy, relatedness). Implication: prefer competence/relatedness signals ("decisions you've preserved for the team," "you just saved the next person from re-deriving this") over competitive leaderboards; keep it optional.

**In-flow prompting is the proven low-friction pattern.** Async standup bots demonstrate that prompting people for structured updates inside Slack at the right time, without a meeting, drives high participation. Geekbot reports 200,000+ users across companies including GitLab, Netflix, and Shopify; a named customer (Chris Brisson, CEO of CallLoop.com & SalesMessage.com) describes the value as "a simple way to get feedback from the team without bothering them." The lesson for Recorder: prompt in-thread, make response one tap, never force a context switch.

### 5. The novel technical architecture — which Slack technologies to combine
The combination most likely to read as "no one has done this" to a hackathon judge:

**(a) Agents & AI Apps framework (split-view assistant + `app_mention`).** Slack's 2024–2026 flagship surface: dedicated split-view container, `assistant_thread_started` / `assistant_thread_context_changed` / `message.im` events, `assistant.threads.setSuggestedPrompts`, `assistant.threads.setStatus`, and text streaming via `chat.startStream`/`appendStream`/`stopStream`. Bolt for Python/JS provide an `Assistant` class and `say_stream` helper. Requires the `assistant:write` scope (auto-added when the feature is enabled). Agents can be invoked anywhere via `@mention`.

**(b) In-flow capture via message shortcuts + ephemeral confirm or modal.** Message shortcuts appear in any message's context menu; a `trigger_id` (3-second TTL, single-use) opens a modal for structured confirm/capture. The killer low-friction variant: passive detection fires an *ephemeral* in-thread prompt with Block Kit buttons ("Log this decision ✓ / Not a decision ✗"), so confirmation is one tap and visible only to the author — zero channel noise.

**(c) Evidence-only Canvas as queryable memory.** `canvases.create` / `canvases.edit` / `canvases.sections.lookup` store the institutional record as markdown with native Slack message-permalink unfurls. The strict rule (the Canvas NEVER contains a generated sentence that wasn't in a real message) is enforced architecturally: the Canvas holds only links, counts, and pointers.

**The "no one has combined these" pitch:** a passive NLP detector → ephemeral in-flow confirmation → an evidence-only Canvas "team memory" → `/why` retrieval, all inside the native Agents & AI Apps surface, with a closed-loop verifier. Most Slack bots do standups (Geekbot) or summaries (Slack AI); none combine in-flow decision capture + a no-synthetic-drift Canvas + commitment verification.

### 6. Workspace-wide access — scopes and the current reality
- **Primary retrieval path: Real-time Search API (`assistant.search.context`).** RTS reached **general availability in early 2026** — it is no longer partner-gated. It uses granular `search:read.*` scopes (`search:read.public` for public channels, `search:read.private` for private channels, `search:read.im` for DMs — only if scoped). Unlike the old legacy `search:read` scope, these granular scopes do not leak DMs unless explicitly requested, making RTS the cleaner and safer choice. Rate limit: **Tier 2 (20+/min)**. Important constraint: RTS cannot be called freely with a static bot token — your app receives an `action_token` inside event payloads (e.g., `app_mention`, `message.im`) and must pass that token to `assistant.search.context`. This means `/why` retrieval must be routed through the Agents & AI Apps container (where `action_token` is available), not a bare slash command invocation.
- **Legacy fallback (`search.messages`):** Still available with a `search:read` user token (xoxp) obtained via OAuth. Tier 2 (20+/min). Use only if RTS is unavailable for any reason — it is a legacy scope, returns DMs regardless of intent, and will eventually be deprecated. Not the recommended primary path.
- **Semantic search:** Available on workspaces with a Slack AI Search plan. The Developer Program sandbox provisions Enterprise Grid features — confirm whether Slack AI Search is included in your sandbox tier. If not, RTS still supports keyword search which is sufficient for `/why [topic]` retrieval.
- **Other scopes the bot needs:** `app_mentions:read` (be @-mentioned anywhere), `channels:history`/`groups:history` (read thread context — but see rate limits), `users:read` (resolve authors for the bus-factor graph), `canvases:write`/`canvases:read`, `chat:write`, `reactions:read` (emoji as signal). On **Enterprise Grid**, an org-ready app with a single org-level user token can query across every workspace the user and app share.

### 7. Storage architecture — evidence-only, minimization by design
The "no synthetic summary" rule is simultaneously a storage-minimization strategy and Slack-policy alignment:
- **Store pointers, not content.** Slack's own agent guidance explicitly states: "Do not store any Slack data you obtain. Instead, store metadata and pull in data in real time if needed." This is *exactly* the SIGNAL Canvas rule — and it's now official Slack best practice. Recorder stores per artifact: `channel_id`, message `ts`, permalink, detected type, owner `user_id`, detection confidence, and status — never the message text.
- **Footprint:** A pointer record is on the order of ~150–300 bytes (IDs, ts, a URL, an enum, a confidence float). Even 100,000 captured artifacts is on the order of tens of megabytes — trivial. Message text is fetched live at query time, respecting the querying user's own access.
- **Dedup/compress over time:** repeat-question clustering naturally dedups (one canonical pointer + a count of recurrences); superseded decisions link forward (ADR-style "superseded by") rather than being rewritten, preserving an append-only audit log.
- **Canvas limits:** No published numeric character/section caps, but `canvases.edit` returns a `canvas_too_large` error when overfull and supports only one operation per call; markdown tables cap at **300 cells**; only markdown (h1–h3, lists, tables, unfurls, mentions) is supported — **Block Kit is not supported in canvases.** So the Canvas should be a concise *index* of pointers, with detail pulled live.

### 8. Closed-loop verification — the genuinely differentiated mechanism
The team's core frustration ("open loops where people say things but nothing verifies what happened") is addressable and is the strongest differentiator.
- **Prior art is thin and mostly meeting/goal-based.** Commitment-lifecycle modeling exists in Microsoft's patents (created→discharged states). Consumer accountability tools show the design space — StickK's "commitment contracts" with referees and financial stakes; ReliablyME's nudges + verification badges; Claryti's bi-directional "what you owe / what others owe you" tracking — but none verify a Slack-stated commitment against later Slack evidence.
- **Recommended verification design for Recorder:**
  1. **Capture** a commitment with an inferred owner + due signal ("I'll deploy staging by Friday").
  2. **Schedule a follow-up** at/after the due time (Slack reminder / scheduled message).
  3. **Verify by evidence search, not by asking**: query for later messages that satisfy the commitment (e.g., a "deployed/merged/done" message from the owner in the relevant channel; a ✅ reaction on the original; a linked PR/closed ticket). Use NLI/LLM entailment to check whether later messages *satisfy* the original commitment.
  4. **Only if no evidence is found**, post a gentle, private nudge to the owner ("Did 'staging by Friday' land? Tap to confirm / reschedule"). This keeps the loop closed with minimal nagging.
  5. **Mark status** (kept / overdue / superseded / forgotten) on the pointer record and reflect a *count* (not synthetic prose) on the Canvas.
- This turns "decisions" into verifiable, auditable facts and folds in contradiction detection: a later message that contradicts an earlier decision is itself a verification signal.

### 9. Technical constraints & gotchas
- **History rate limits are brutal for non-Marketplace apps.** As of changes effective May 29, 2025 (existing installs March 3, 2026), `conversations.history` and `conversations.replies` drop to **Tier 1 (1 request/min, max 15 objects/request)** for commercially distributed non-Marketplace apps. **Internal customer-built apps keep ~50+/min (Tier 3, up to 1,000 objects).** Implication: build Recorder as an *internal app*, process messages live via the Events API rather than back-filling history, and never architect around bulk history pulls. Real projects (e.g., the ZeroClaw issue tracker) document 429s dropping channel context and the need for `Retry-After` backoff + caching.
- **RTS `action_token` pattern — design around this early.** The Real-time Search API is not freely callable with a bot token. Your app receives an `action_token` only from specific event payloads (app mentions, DMs to the assistant). This means `/why [topic]` must be triggered through the Agents & AI Apps surface (an `@mention` or DM to Recorder) rather than a bare slash command — slash commands do not yield an `action_token`. Design the UX around this from the start rather than retrofitting it later.
- **Latency for in-flow prompting:** interaction payloads (shortcuts/modals) must be ack'd within **3 seconds** or the user sees an error; `trigger_id` expires in 3 seconds and is single-use. Pattern: ack immediately, do detection/LLM work async, then post the ephemeral confirm. Use Socket Mode for local/hackathon dev; use text streaming (`chat.startStream`) to feel responsive on longer answers.
- **Free vs paid:** the Agents & AI Apps *agent container* requires a paid plan; free teams can only create channel-tabbed (not standalone) Canvases (errors `free_teams_cannot_create_non_tabbed_canvases` / `free_teams_cannot_edit_standalone_canvases`). **Use a free Slack Developer Program sandbox**, which provisions all paid Enterprise Grid features for free — the single most important hackathon setup decision.
- **Classic-app deprecation:** Legacy classic apps are set to be deprecated **November 2026** — migrate to modern Slack apps. This doesn't affect Recorder if built fresh on the modern platform, but avoid any tutorial code that uses the old RTM API.
- **Other known challenges:** semantic search requires a Slack AI Search plan (confirm sandbox tier); DMs leaking through the legacy `search:read` scope is a privacy gotcha — the granular RTS scopes fix this. `canvases.create` is Tier 2 (20+/min) and `canvases.edit` is Tier 3 (50+/min), so Canvas writes are not a bottleneck.

## Details

**Why "Recorder" beats "reconstructor" tools, evidentially.** The developer-experience and interruption literature establishes that information discovery / institutional-memory loss is the #1 friction point and that lost rationale is a distinct, under-served problem. The failure mode of ADR/Confluence/Notion is consistent across primary sources: capture is manual, lives away from work, and decays. Recorder's wedge is to make capture a one-tap in-flow act and retrieval a Slack-native `/why`, with the Canvas as an *index of evidence* rather than a document that rots.

**Why evidence-only is both ethical and technically superior.** It (a) aligns with Slack's explicit "don't store Slack data, store metadata" guidance; (b) eliminates "synthetic documentation drift" (the bot can never be wrong about what was said, because it only ever points at what was said); (c) minimizes storage and privacy surface; (d) respects per-user access because content is fetched live with the querying user's permissions.

**Why transparency + engaging design (not deception) is the right and only path.** The constraint against disguised/impersonating agents is correct on platform-policy and consent grounds. The HCI evidence shows you don't *need* deception: transparent agents that use reciprocal self-disclosure, peer framing, conscientious reliability, and in-flow low friction already drive high disclosure and engagement. The win comes from *interaction design*, not concealment.

## Recommendations

**Stage 1 — De-risk the platform (do this first, before any feature code).**
- Create an **internal app in a free Slack Developer Program sandbox** (unlocks paid Enterprise Grid features + standalone Canvases, keeps Tier 3 history limits).
- Enable the **Agents & AI Apps feature** on your app — this is required for RTS and for the split-view assistant surface.
- Set up retrieval on **`assistant.search.context` (RTS)** with granular `search:read.public` / `search:read.private` scopes. RTS is GA as of 2026 and is the correct primary path — no partner enrollment needed. Remember: retrieval must be triggered via `app_mention` or DM to get the `action_token`; plan your `/why` UX around this.
- Keep legacy `search.messages` as a fallback only if RTS fails in testing for any reason.

**Stage 2 — Build the in-flow capture loop (the demo centerpiece).**
- Subscribe to `message`/`app_mention` events; run a high-recall **LLM decision/commitment classifier** on new messages.
- On a hit, post an **ephemeral in-thread Block Kit confirm** ("Log this decision? ✓/✗") — one tap, author-only. On confirm, write a **pointer record** and unfurl it into the team **Canvas**.
- Ship `/why [topic]` retrieval returning ranked permalinks with original messages pulled live.

**Stage 3 — Add the closed-loop verifier (the differentiator).**
- For confirmed commitments, schedule a follow-up; verify by **evidence search + NLI entailment** before nudging; mark kept/overdue/superseded; reflect counts on the Canvas.

**Stage 4 — Layer in passive intelligence as time allows.**
- Repeat-question clustering (embeddings + cosine), bus-factor heuristic (thread-participation concentration), contradiction detector (similarity-retrieve → NLI). Each is independently demoable.

**Persona/tone to ship:** senior-dev peer; concise, factual, lightly warm; opens with brief self-disclosure of its reasoning; sparing wit; optional competence/relatedness gamification ("decisions you've preserved"), no competitive leaderboard; formality scales up for higher-stakes commitments.

**Benchmarks that would change the plan:**
- If RTS keyword search proves insufficient for retrieval quality → explore whether Slack AI Search (semantic search) is available in your sandbox tier and upgrade if so.
- If false-positive rate on decision detection annoys users in testing → raise the confidence threshold and/or switch from passive auto-prompt to user-initiated message-shortcut capture.
- If targeting real distribution → must go through Slack Marketplace review (the only sanctioned commercial-distribution channel) to regain Tier 3 history limits.

## Caveats
- **RTS is GA but has an architectural constraint:** `assistant.search.context` requires an `action_token` from event payloads — it is not freely callable with a static bot token. The `/why` retrieval flow must be designed around the Agents & AI Apps surface (mentions/DMs) to receive this token. Test this early in Stage 1 before building retrieval logic around it.
- **Commitment-completion statistics from vendors (Claryti's "91% vs 61%," "39% never completed") are self-reported marketing**, not peer-reviewed — cite as vendor claims only.
- **Gamification can backfire** on engagement/well-being for some workers; keep it optional and intrinsic-motivation-aligned.
- **Detection precision/recall in a hackathon LLM-prompt approach will be imperfect**; design the UX so false positives are one-tap dismissible and false negatives are recoverable via the message shortcut.
- **Bus-factor from thread participation is a proxy**, not a validated measure; present it as a "knowledge-concentration signal," not a definitive metric.
- **Several persona/self-disclosure studies come from mental-health/companion-bot contexts** (e.g., the conscientiousness finding from Völkel & Kaya; reciprocity from Liang et al.). The *direction* of effects (reciprocity, conscientiousness, moderate personality) is robust across contexts, but exact effect sizes may not transfer cleanly to a workplace scribe. The 47-participant longitudinal figure is confirmed; an earlier draft's "53-user" figure could not be verified and has been removed.
